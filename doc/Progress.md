## Folder layout decision

PLAN.md specifies `backend/app/...` (lowercase). Kept the existing top-level `Backend/` and `Frontend/`
folder names as-is (Windows/git case-only renames are fragile and not worth the risk), but introduced
`Backend/app/` as the package root for the new pandas-based architecture, matching the plan's *internal*
structure exactly from here on (`app/dataframe/`, and `app/models`, `app/nodes`, etc. in later phases).

The old flat `Backend/models/`, `Backend/nodes/`, `Backend/parsers/` (pure-Python, pre-existing) are left
untouched for now — they have their own passing tests (`test_models.py`, `test_parsers.py`) and nothing
in Phase 1 depends on them. They'll be retired/migrated into `app/` as each corresponding phase reaches
them (nodes/base.py in Phase 2, csv_io in Phase 4) rather than all at once.

**Files added:**

## Phase 5b — Transform nodes (9 nodes) — ✅ DONE (checkpoint 2 of Phase 5)

**Files added** (`Backend/app/nodes/transform/`, one file each): `filter_node.py`, `sort_node.py`, `select_columns.py`, `rename_column.py`, `limit_rows.py`, `remove_duplicates.py`, `fill_missing.py`, `convert_type.py`, `add_calculated_column.py`. All 9 registered in `build_registry()`. Tests: one module per node under `Backend/tests/nodes/` (`test_filter_node.py` … `test_add_calculated_column.py`), 88 tests total.

**Cross-cutting decision — Excel column references are unresolvable placeholders.** `to_excel_formula(input_ref, config)`'s signature (§5) has no access to the input schema, so no node can ever compute a real Excel cell/column reference (a letter or index) for a given column name — the plan's own examples (`{column_ref}`, `{col_index}`) assume information the interface doesn't provide. Every node in this checkpoint that needs a column reference renders it as a bracketed placeholder instead, e.g. `[age]` — `FILTER(Sheet1!A1:Z1000, [age]>30)` rather than a resolved range. This is applied consistently (filter, sort, fill_missing, convert_type, select_columns, add_calculated_column) and documented in each file. Worth a firmer decision in Phase 7 (`formula_engine.py`) — either accept bracketed placeholders as the permanent output format (and say so plainly in the Formula Panel UI), or extend `to_excel_formula`'s signature to also receive the schema, which would touch every node built so far.

**Per-node notes:**
- **filter / sort** — both declare only the plan's literal primary-condition/primary-key config fields in `get_config_schema()`, but `execute()` also honors an optional second condition group (`column2`/`operator2`/`value2` + `logic`) and multi-key sort (`sort_keys: [{column, direction}, ...]`) respectively — the plan describes both capabilities in prose without giving field names. Sort's exported Excel formula only encodes the primary key (matches the plan's literal single-key `SORT()` pattern); extra keys are called out by name in the explanation text rather than silently dropped.
- **select_columns** — the plan gives no `to_excel_formula` spec for this node at all (unlike every sibling, and not in §8.1's explicit not-supported list either). Treated as an oversight and filled in with `CHOOSECOLS()`, Excel 365's real dynamic-array column-selection function, rather than defaulting to `None`.
- **rename_column** — `config["mappings"]` is a list of `{from, to}` dicts; `get_config_schema()` returns one nominal field since the plan says the frontend special-cases this node's UI entirely (§13).
- **fill_missing** — the plan's one formula pattern (`IF(ISBLANK(ref), fill_value, ref)`) only really fits the `fixed` strategy; extended it to substitute `AVERAGE()`/`MEDIAN()` for those strategies inside the same `IF` wrapper. `previous` (forward-fill) has no honest single-formula Excel equivalent (needs "nearest non-blank cell above"), so `to_excel_formula` returns `None` specifically for that strategy rather than emitting something wrong.
- **convert_type** — uses `errors="coerce"` throughout per spec. **Not yet resolved:** `NodeResult.error_row_indices` (§7.1, "populated for row-level failures (type conversion...)") needs the executor to diff null-ness on the target column before/after `execute()` — this node doesn't (and structurally can't, per its `execute(df, config) -> FluxDataFrame` signature) report which rows failed on its own. Flagging for Phase 6.
- **add_calculated_column** — the big one. Built a real tokenizer + recursive-descent parser + tree-walking evaluator for `config["expression"]` (a string like `"price * quantity + 10"` or `"IF(price > 100, price * 0.9, price)"`) instead of using Python's `eval()`, per the plan's explicit security requirement. Evaluation is fully vectorized against pandas Series (no per-row Python loop). Two real bugs were caught and fixed during testing, not just design choices:
  1. The initial grammar only allowed comparison operators (`= ≠ > < ≥ ≤`) inside `IF(...)`'s condition — a standalone boolean expression like `"price > 10"` (a very reasonable calculated-column use case) failed to parse. Fixed by promoting comparisons to their own precedence level (`comparison := additive (COMP additive)?`) available anywhere an expression can appear, not just inside `IF`.
  2. `infer_output_schema`'s static type-checker short-circuited on arithmetic operators (`+ - * /`) and returned `NUMBER` without recursing into the operands — so `"missing_col + 1"` silently passed validation instead of raising `SchemaValidationError` for the unknown column. Fixed by always recursively type-checking both operands (for validation) even when the operator alone already determines the result type.
  - Formula export (`to_excel_formula`) does **not** wrap `input_ref` the way every other transform node does — the plan's bullet for this node never mentions `{input_ref}`, because a calculated column is inherently a per-row formula (like `=[@price]*[@quantity]` in an Excel Table), not a whole-range transform. This breaks the assumption in §8.1's `compose()` that every node's formula nests inside its parent's. **Flagging explicitly for Phase 7**: `engine/formula_engine.py` will need to special-case `add_calculated_column` (e.g. treat it as a side/terminal formula rather than nesting it) rather than assuming uniform chain composition.

**Test status:** 194/194 passing (106 previous + 88 new).

**group_by_aggregate / pivot share `AGGREGATE_FUNCTIONS`/`PANDAS_FUNC_MAP`** (`SUM→sum, AVERAGE→mean, COUNT→count, MIN→min, MAX→max, COUNT_DISTINCT→nunique`), exported from `group_by_aggregate.py` and imported by `pivot.py` — the plan gives this exact function set for `group_by_aggregate` and reuses "aggregate_function" for `pivot` without restating the enum, so sharing one definition seemed clearly right rather than a premature abstraction (contrast with the earlier decision *not* to share the 3-line `_looks_numeric` helper — this is a meaningful shared vocabulary, not a trivial one-liner).

Excel export only renders the *first* aggregation as `SUMIF`/`AVERAGEIF`/`COUNTIF`/`MINIFS`/`MAXIFS` wrapped in `UNIQUE(group_ref)` to spill one row per group (real, valid Excel 365 array-criteria behavior, not invented) — same "document what's dropped" treatment as sort's multi-key limitation from 5b. `COUNT_DISTINCT` has no single-formula Excel equivalent, so it's skipped even as the primary aggregation.
- **pivot** — `infer_output_schema` can only ever guarantee the `row_column` — the real output columns are whatever distinct values are in `column_column`, unknowable without executing (same structural limit as source nodes' stub schemas in 5a). `execute()` builds the *real* schema itself straight from the pivoted DataFrame's actual pandas dtypes (via a small `_dtype_to_data_type` mapper), bypassing `infer_output_schema` entirely for the real run. `to_excel_formula` always returns `None`; confirmed this alone is sufficient for the plan's suggested `formula_exportable` catalogue flag (§8.1) to correctly read `False` for pivot with zero hardcoding needed in Phase 10, since the generic `plugin.to_excel_formula(None, {}) is not None` check just works.
- **join** — hit the same class of interface gap as `execute_source` in Phase 5a: `infer_output_schema(self, input_schema, config)` only takes one schema, but a join genuinely needs both sides'. Resolved with the *same* reserved-config-key convention already established: `input_schema` = left parent's schema, `config["_right_schema"]` = right parent's schema, to be injected by the executor (Phase 6) — consistent rather than inventing a second mechanism. (`execute_join()` itself doesn't have this problem — it already receives both `FluxDataFrame`s directly.) `_merged_schema()` replicates pandas' actual merge column-naming behavior exactly, verified by direct experiment: same-named join keys collapse to one unsuffixed column; different-named keys both survive unsuffixed; only genuinely overlapping *non-key* columns get `_left`/`_right` suffixes. Excel export (`XLOOKUP`) only covers `LEFT`/`INNER` per the plan's literal spec — `RIGHT`/`FULL` return `None` since XLOOKUP has no right/full-outer equivalent, with the explanation text saying so explicitly rather than emitting something wrong.

**Naming:** class is `DAGExecutor` per §3's project-structure comment (`executor.py # DAGExecutor, Kahn's algorithm...`); §15's testing section calls it `DagExecutor`. Treated as the same inconsistent capitalization, not two different things.

**Three real gaps in the plan's literal spec, resolved (all documented in the module's own docstring, not just here):**
1. **Cycle/pipeline-level errors have no home in `ExecutionResult`.** §7.2 step 3 says a cycle should "return error: ...", but `ExecutionResult` is strictly `{node_results: dict[str, NodeResult]}` with no top-level error field. Rather than extending the schema, every node caught in a cycle gets its own `NodeResult(success=False, error_message="Your pipeline has a cycle involving: ...")`, naming the whole cycle — and since Kahn's algorithm already guarantees every node *outside* the cycle reaches a valid topological position, they execute completely normally in the same run. Verified with a scratch test: a 3-node cycle plus a fully independent 2-node branch in the same request — the independent branch ran successfully while the cycle's 3 nodes each got the cycle error.
2. **One pipeline-level `csv_data`/`data_reference_id` pair can't feed a `join`'s two independent sources.** `PipelineRequest` has exactly one slot for inline/cached data, but a join needs two separately-uploaded source nodes. Resolved by resolving data *per source node*: each source node's own `config["csv_data"]`/`config["data_reference_id"]` is checked first, falling back to the pipeline-level fields only when absent. Single-source pipelines work exactly as literally specified (zero extra steps, uses the fallback); the two-source join test (`test_join_pipeline_with_two_independent_sources`) confirms the multi-source path actually works.
3. **Malformed edges referencing an unknown node id** are silently dropped during graph building rather than raising — same "nowhere to put a whole-request error" reasoning as #1; a request malformed at this level has no single node to blame either. Covered by `test_malformed_edge_to_unknown_node_is_dropped_not_fatal`.

**Confirmed, not just assumed:** `join`'s `execute_join()` needs none of the `config["_right_schema"]` injection convention established in Phase 5c for `infer_output_schema` — `execute_join()` already receives both real `FluxDataFrame`s directly from `node_outputs` via `parents_by_port`, so the executor just looks them up and calls it. The `_right_schema` convention only matters for `/api/pipeline/validate-edge`, which doesn't exist yet (Phase 10).

**Data-resolution priority, for the record:** per source node, `config["data_reference_id"]` → `request.data_reference_id` → (if `read_csv`) `config["csv_data"]` → `request.csv_data` → none (node's own `execute_source` raises its existing "no data available" `SchemaValidationError` from Phase 5a, unchanged).

## Phase 7 — `engine/formula_engine.py` (forward + reverse) — ✅ DONE

**The two items flagged as open from Phases 5b/6 are now resolved:**
- **`join` (two parents, one `find_parent()`).** Confirmed via Phase 6's own finding that `execute_join()`/`to_excel_formula()` never consume `input_ref` — so `_compose()` special-cases `join` to skip recursing into either parent entirely for formula purposes, calling `to_excel_formula(None, config)` directly (same treatment as a source-node base case). - **`add_calculated_column` (per-row formula, not a range transform).** Resolved with a terminal-position check in `_compose()`: as the *last* node in the pipeline, its own rendered expression tree is the final formula (what the user actually wants to see). Anywhere else in the chain, `_compose()` passes the *parent's* formula straight through unchanged for downstream wrapping — correct because adding a calculated column in real Excel doesn't change what range subsequent formulas reference. Verified both cases directly: terminal → `=([price]*[quantity])`; non-terminal followed by `sort` → `=SORT(Sheet1!A1:Z1000, [total], 1)` (wraps the *original* range, not the calculated expression).

**A third, related consistency gap was caught and fixed while building this phase, in a Phase-5c file:** `group_by_aggregate.to_excel_formula_explanation()` didn't mention "no Excel equivalent" when the primary aggregation is `COUNT_DISTINCT` (the one case where its `to_excel_formula` returns `None`), unlike every other None-returning node in the codebase (`pivot`, `rename_column`, `limit_rows`, `fill_missing`'s `previous` strategy, chart nodes, `join`'s RIGHT/FULL case all already explained themselves). Patched to add the same self-explaining note, since the whole point of always appending a node's explanation during `_compose()` — even when its formula is `None` — is exactly this: telling the user *why* the chain stopped there. All 294 pre-existing tests still passed after the one-line patch.

**Real bug caught by the manual smoke-test pass, not by writing tests first:** the initial `parse()` implementation reused the same recursive `_parse_node_chain()` helper for both the top-level input *and* nested range arguments. That helper's fallback behavior — "not a recognized function call? treat it as a literal range reference and emit a generic source node" — is correct and necessary for nested arguments (e.g. `FILTER`'s range argument legitimately can be a bare `Sheet1!A1:Z1000`), but wrong at the top level: `engine.parse("not a formula at all")` was silently succeeding with a trivial one-node "pipeline" instead of returning a `ParseError`. Fixed by giving `parse()` its own top-level check that requires the *whole* input to be a recognized function call, while `_parse_node_chain()` keeps the lenient fallback for nested arguments only.

**Reverse-parsing scope, beyond the plan's literal 8 patterns:** implemented 11 — the plan's `FILTER`, `SORT`, `UNIQUE`, `XLOOKUP`, `VLOOKUP`, `SUMIFS`, `AVERAGEIFS`, `COUNTIFS`, plus singular `SUMIF`/`AVERAGEIF`/`COUNTIF`. The singular forms exist because `group_by_aggregate`'s forward direction (Phase 5c) actually *generates* singular `SUMIF`/`AVERAGEIF`/`COUNTIF`, not the plural `*IFS` forms — without registering the singular patterns too, this engine's own forward output couldn't be round-tripped back through its own reverse parser. Verified directly: `SUMIF([region], UNIQUE([region]), [sales])` → `group_by_aggregate` node with the original group/aggregation config recovered exactly. The plural `*IFS` forms are supported for exactly one criteria-range/criteria pair (the only shape our node model can represent); a multi-criteria call returns a `ParseError` explaining that boundary explicitly rather than silently dropping extra criteria pairs.

**Recursion is unbounded depth but fixed, small vocabulary** — not the "simple bracket-matching, not a full tokenizer" the plan describes for the *outer* function name (still true: `extract_call_parts()` is exactly that, a single regex plus a hand-rolled top-level-comma splitter that respects nested parens/brackets/quotes), but nested range arguments recursively re-enter the same pattern matcher, so `UNIQUE(FILTER(Sheet1!A1:Z1000, [status]="active"))` correctly reconstructs a 3-node chain (source → filter → remove_duplicates), verified directly. This is still "pattern matching on a fixed, documented set of shapes," per §8.2 — never a general Excel expression parser — since only the 11 registered function names are recognized at any depth; anything else terminates as a generic `read_csv` placeholder node (not silently mis-parsed, and not executable as-is, since it lacks the real `_csv_text` config key `read_csv.execute_source()` requires — it's meant as a starting point the user attaches real data to, with `config["_source_range"]` preserved as a frontend hint).

**Compatibility detection** (`determine_compatibility`, §8.1's example: `"Requires Excel 365 (dynamic arrays)"`) implemented as a simple substring scan for `FILTER(`/`SORT(`/`UNIQUE(`/`XLOOKUP(`/`CHOOSECOLS(` in the generated formula; anything else generated gets `"Compatible with Excel 2016 and later"` (covers `VALUE`/`TEXT`/`DATEVALUE`/`IF`/`SUMIF`/`AVERAGEIF`/`COUNTIF`/`MINIFS`/`MAXIFS`, all pre-365 functions); `None` formulas get `"N/A — no formula available for this pipeline"`.

**Rate limiting required real investigation, not just `@limiter.limit(...)`.** §12 asks for limits "more aggressive for unauthenticated requests... since there's no per-user quota to lean on otherwise." Read `slowapi`'s actual source (`inspect.getsource`) before assuming an API: dynamic `limit_value` callables only ever receive the rate-limit *key* (e.g. the IP string) or nothing — never the request/headers (`LimitGroup.__iter__`) — so they structurally can't check `Authorization` themselves. `exempt_when` callables *can* take a `Request` (confirmed in source), but `Limit.is_exempt` calls them synchronously, never awaited — too restrictive for the app's real auth check, which is async and hits the database. Resolved with two stacked `@limiter.limit(...)` decorators per route (`tiered_rate_limit()`): a strict limit (`10/minute`) exempted for requests carrying a *validly-signed* JWT, checked via a lightweight **synchronous** signature-only verification using PyJWT directly (no DB call) — and a generous limit (`60/minute`) that always applies. Deliberately checks signature validity only, not whether the user still exists/is active: confirmed directly that a garbage/forged bearer token fails `jwt.decode()` and correctly falls back to the strict tier — closing the obvious "just send any Authorization header" bypass — while still not duplicating the route's own real, DB-backed `current_user_optional`/`current_active_user` check. Verified empirically end-to-end (not just unit-level): 12 rapid guest requests to `/api/pipeline/execute` → exactly 10 succeed, then `429`; the same request pattern with a real token from a real registered user → all 15 succeed.

## Build Order Item 23 — End-to-End Guest → Sign-Up Test — ✅ DONE

**The literal acceptance test from PLAN.md's Build Order:** "as a guest, upload the student-grades CSV, build filter + group-by + chart, verify formula generates, then sign up mid-session and confirm the in-progress pipeline saves correctly." **Found and fixed a real, significant guest-mode bug in the process: the 10/minute guest rate limit on `/api/pipeline/execute` was far too low for ordinary interactive use.** Building even this modest 4-node pipeline — drag 3 nodes, connect 3 edges, edit 3 fields on Filter, 2 on Group By Aggregate, 3 on Bar Chart — fires a debounced execute call after nearly every one of those actions (each one is a separate user action spaced further apart than the 300ms debounce window, so they don't coalesce into one call). That alone is over a dozen calls inside a minute, blowing past the old 10/minute ceiling almost immediately during completely normal use. Once rate-limited, the failure was silent and permanent from the user's perspective: `ReactFlowCanvas.jsx`'s `runExecution` only ever called `setNodeResults` on success, so a 429 just left `nodeResults` frozen on whatever the last successful response happened to contain — in this case, an early snapshot from before the Filter node's config was even set, displaying a stale "Column 'None' not found" error indefinitely with zero indication anything had gone wrong. This directly undercuts §12's core promise ("guests get the full building/running/exporting experience") — it breaks under the very interaction pattern that promise describes. Diagnosed by instrumenting the Playwright script with request/response listeners on `/api/pipeline/execute` (not visible from the UI or from reading source alone) and watching real `429` responses arrive right where the canvas appeared stuck.

Fixed on two sides:
- **`Backend/app/rate_limit.py`**: `GUEST_LIMIT` raised from `10/minute` to `30/minute` — still meaningfully tiered below `AUTHENTICATED_LIMIT` (60/minute) per §12's "more aggressively than authenticated" requirement, but enough headroom for realistic interactive pipeline building. Updated the three rate-limit tests in `test_api.py` that hardcoded the old threshold (`test_pipeline_execute_guest_rate_limit_trips_after_ten` → `_after_thirty`, the authenticated-tier comparison test, and the upload rate-limit test, which shares the same `GUEST_LIMIT` constant). 393/393 backend tests still pass.
- **`Frontend/src/store/pipelineStore.js` / `ReactFlowCanvas.jsx`**: added `executionError` state, set whenever an execute call fails outright (network error, 429, 5xx) and cleared on the next success — as opposed to a node-level error, which already arrives as a normal 200 with that one node's result marked unsuccessful. A small banner now surfaces it directly on the canvas (top-center, not blocking interaction), with a specific message for the rate-limited case ("You're editing faster than the server can keep up…") versus a generic one for anything else. This doesn't prevent hitting a limit under heavy enough use, but it means a guest is never again left staring at a frozen, unexplained error with no idea their last edit silently didn't take effect.
